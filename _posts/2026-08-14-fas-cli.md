At work I've been using Azure AI Foundry to deploy AI Agents, so it is fair to say that I have spent now
a fair amount of time around Azure development tooling options.

Azure provides the [Azure Developer CLI (`azd`)](https://learn.microsoft.com/en-us/azure/developer/azure-developer-cli/), and according to Microsoft it
**should** accelerate your path from a local development environment to Azure. 

However in my experience the tooling usage been convoluted and slow. So I decided to benchmark it:
using `azd` to deploy against Azure AI Foundry, starting from nothing. How
long until a deployed model and its agent can actually answer an inference
request?

Across 5 runs, `azd` averaged 22.5s for a model deployment plus a simple
prompt agent. Curious where that time actually went, I dug through `azd`'s
debug log, tracing the calls with Claude's help.

## Where the 22.5s goes

Before `azd` touches the network at all, it shells out to a separate Bicep
compiler three times to turn the template into something Azure Resource Manager, or ARM can read. 
For those unfamiliar with Azure, ARM is the API layer that Azure deployments ultimately go through. Whether you deploy with the Azure Portal, az, Bicep, Terraform, or azd, those tools eventually translate your intent into requests to Azure’s resource management APIs.

Going back to my experiment, just compiling the Bicep templates takes about 9 seconds on my laptop, and this is before a single request leaves the machine.

And after this, it has to deal with the fact that ARM also tracks the deployment itself. azd validates that deployment, submits it, and polls its status until ARM says it has succeeded. In my trace, that meant roughly half a dozen additional round-trips before the resource I actually asked for was even confirmed. Call it another 5 seconds spent watching the deployment wrapper rather than the thing being deployed.

The last chunk is different. Not everything in an agent stack can be provisioned through the ARM template, and creating the agent itself requires going through the Foundry APIs. So azd hands off to a hook script, which spins up an entire Python interpreter just to make one API call.

## Why azd does this

I've worked as a platform engineer, and I get why this exists when the job is managing real infrastructure. Bicep compilation, the ARM wrapper, and deployment state tracking buy real things in production: declarative and idempotent deployments, dependency ordering, validation, and a consistent audit trail for infrastructure where everything depends on everything else—networking, IAM, and dozens of resource types.

None of that buys me anything when I just want to get a model and a prompt
agent live. I don't think `azd` is bad tooling. I think it's built for a
different job than the one I'm doing. 

Agent definitions sit much closer to business logic than infrastructure, and they change on a completely different cadence. I don't think updating a prompt, changing a tool, or tweaking an agent definition should have to pass through the same pipeline as networking, IAM, and other long-lived infrastructure. When I'm iterating on an agent, I might make those changes several times an hour, not once a quarter.

## The trade-off isn't mandatory

What IaC is supposed to buy you (repeatability, idempotency, change detection, an audit trail) doesn't inherently require a Terraform-style state file or ARM's tracked deployment wrapper. Those are ways of implementing those guarantees, not the guarantees themselves. A tool can derive current state from the platform APIs, rely on idempotent resource operations, and keep history elsewhere. ARM's choice to wrap every deployment in a tracked resource is reasonable for the infrastructure workloads it was designed for, but it isn't the only possible design.

I'm also not the only one drawing this line. Microsoft's own GitOps
reference architecture for [Foundry Hosted Agents](https://techcommunity.microsoft.com/blog/azuredevcommunityblog/building-and-operating-a-microsoft-foundry-hosted-agent-with-gitops-and-github-t/4523393)
makes the same call. `/infra` (Bicep) stays separate from `/src/prompts`,
`/src/agents`, `/src/tools`. Prompts are plain text files, reviewed via PR,
baked into a container image, and promoted by tag. They never get re-run
through Bicep. A prompt change isn't an infrastructure change, and treating
it like one just adds friction.

AWS and Google have quietly landed on the same split. [Bedrock AgentCore now
offers a zip-based direct deploy path](https://aws.amazon.com/blogs/machine-learning/iterate-faster-with-amazon-bedrock-agentcore-runtime-direct-code-deployment/)
alongside its CDK/CloudFormation one, and the same split shows up in the
wild for Vertex AI Agent Engine: [one writeup suggests deploying with the Python SDK are fine for
quick iteration and suggests Terraform for a more mature set up](https://dev.to/toyama0919/deploying-a-google-adk-agent-to-vertex-ai-agent-engine-with-terraform-83b).
Neither vendor calls the fast path production-ready, though. Both frame it as
a prototyping on-ramp you're meant to graduate off of. 

## fas: split by change frequency, not by resource type

With that in mind I built [`fas-cli`](https://github.com/) (foundry agents
stack). Connections, toolboxes, and agent definitions change often, so `fas`
deploys straight through the SDK, no Bicep, and diffs against live Azure on
every `fas plan`. It deploys a model and a running prompt agent in 10s,
against `azd`'s 22.5s average.

|                        | `azd` / Bicep                          | `fas`                                  |
|------------------------|-----------------------------------------|-----------------------------------------|
| Deploy time (model + prompt agent) | 22.5s avg (5 runs)          | 10s avg (5 runs)                        |
| State                  | ARM deployment history + Bicep compile  | None, reads Azure live on every `plan`  |
| Reconciliation model   | Diff against last-applied state         | Diff against live Azure, every time     |
| Dependency execution   | Sequential ARM deployment wrapper       | DAG from typed references, run concurrently |
| Concurrency control    | ARM deployment locking                  | Optimistic, no lock (see below)         |
| Scope                  | Any ARM resource, subscription-wide     | Foundry accounts/projects only          |

Three things make it fast.

No state file. `fas plan` reads Azure directly and diffs against the Python
definitions. There's nothing to cache, so there's nothing to go stale. The
trade-off is real: there's no local history of past deployments to roll back
to. If something breaks, you fix the Python and redeploy. Azure's own state
and your git history are the record; there isn't a separate one.

A real dependency graph instead of a hardcoded chain. `fas` builds the DAG
from the typed references already in your code and runs the independent
pieces concurrently instead of walking a fixed order.

Optimistic concurrency instead of locking, and this one has a real failure
mode worth stating plainly. `apply()` checks nothing has changed since the
last `plan()` before it writes, the same bet git makes on every push. That
works as long as writers don't overlap. Run `fas deploy` twice on the same
project close together, from two people or a person and CI, and the second
write can win silently. No error, no merge conflict, just the earlier change
gone. Fine for one developer or a small team. Once more than one person or
pipeline deploys the same project regularly, this needs a real lock. It
doesn't have one yet. A lock isn't the only fix, either: AgentCore sidesteps
the same problem by versioning every deploy instead of overwriting one
record, so a concurrent write costs you a traffic cutover, not the work
itself. Worth considering here too.

## What fas doesn't do 

`fas` is scoped to Foundry accounts and projects: models, connections,
toolboxes, prompt agents. Not general Azure infrastructure. It doesn't
handle multi-environment promotion (dev to stage to prod), and it doesn't
manage RBAC or service principals for you. And as above, it has no
deployment locking yet. Treat it as it is: 
an experiment from a bored developer, that you can use as a fast loop, not a shared CI target in a production environment.

## And finally: where I land

None of this is an argument against IaC. Terraform and Bicep's
state-file-and-tracked-wrapper model earns its keep when you're managing
infrastructure with real interdependencies that changes rarely. It's just
the wrong shape for agent definitions that change every hour and don't have
ARM resource types to begin with. Match the tooling to how often the thing
actually changes, not to what category of resource it technically is.

If your team is deploying agents through `azd` or Terraform today, I'd like
to know how you're handling this split, or whether you've decided it's not
worth splitting at all.
